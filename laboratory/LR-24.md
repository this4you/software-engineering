# Лабораторна робота: Dockerfile і контейнеризація курсового проекту

## Мета

Навчитися **пакувати власний застосунок у Docker-образ**. У LR-23 ти запускав(ла)
готові образи з Docker Hub; тепер ти напишеш свій `Dockerfile` для **курсового
проекту**, збереш із нього образ, запустиш контейнер і переконаєшся, що проект
працює. Фінал — підготувати **одну команду**, якою викладач локально підніме
твій проект і подивиться на нього, не налаштовуючи нічого вручну.

> Ця лаба — про **твій курсовий**. Сам застосунок ми не пишемо: береш те, що
> вже є, і контейнеризуєш. Якщо курсовий ще зовсім «сирий» — досить, щоб він
> хоча б запускався локально й мав одну видиму сторінку/ендпоінт.

## Передумови

- Пройдена LR-23 (розумієш `image`, `container`, `docker run`, `docker compose`).
- Запущений Docker Desktop.
- Локальна копія твого курсового проекту, який **запускається** на машині
  (знаєш команду старту й порт, який він слухає).
- Безкоштовний акаунт на **hub.docker.com** (для фінального завдання).

> **Що таке Dockerfile.** Це текстовий рецепт збірки образу: з якого базового
> образу стартувати (`FROM`), куди класти файли (`WORKDIR`, `COPY`), що
> встановити (`RUN`), який порт відкрити (`EXPOSE`) і якою командою запускати
> застосунок (`CMD`/`ENTRYPOINT`). Команда `docker build` «готує» за цим
> рецептом образ.

## Як здавати

- **Формат:** файл `lab_dockerfile_<прізвище>.md` або PDF.
- **Структура:**
    1. Титулка (ПІБ, група, дата).
    2. По розділу на кожне з обов'язкових завдань зі скрінами.
    3. (Опціонально) розділ із бонусом.
    4. Розділ «Відповіді на питання».
    5. Чек-лист самоперевірки.
- **Окремо обов'язково:** твій підсумковий `Dockerfile` (текстом) і **команда
  для викладача** (Завдання 6).
- **Скріни:** `![підпис](images/файл.png)`.
- **Здача:** як домовлено з викладачем.

# Частина 1 — Обов'язкові завдання

## Завдання 1 — Написати Dockerfile для свого курсового

У корені проекту створи файл `Dockerfile` (без розширення). Нижче — три
приклади з поясненням рядків. **Візьми той, що відповідає твоєму стеку**, і
адаптуй (версії, шляхи, порт, команду запуску).

### Варіант A — Java / Spring Boot (multi-stage)

```dockerfile
# --- етап 1: збірка ---
FROM gradle:8-jdk21 AS build
WORKDIR /app
COPY . .
RUN gradle bootJar --no-daemon          # або: mvn -q clean package -DskipTests

# --- етап 2: запуск (тільки JRE + готовий jar) ---
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

> **Multi-stage**: перший етап має повний JDK + Gradle і збирає `jar`; у фінальний
> образ копіюється тільки готовий `jar` на легкому JRE. Образ виходить у рази
> менший. (Maven: заміни `RUN gradle …` на `RUN mvn …`, а шлях на `target/*.jar`.)

### Варіант B — Python (Flask / FastAPI / Django)

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
# Flask:    CMD ["flask", "run", "--host=0.0.0.0", "--port=8000"]
# FastAPI:  CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# Django:   CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]
CMD ["python", "app.py"]
```

> Спершу копіюємо лише `requirements.txt` і ставимо залежності, а потім решту
> коду — так Docker кешує крок встановлення й не перевстановлює пакети на кожну
> зміну коду.

### Варіант C — Універсальний (будь-який інший стек)

Принцип однаковий незалежно від мови:

```dockerfile
FROM <базовий-образ-під-твій-стек>    # напр. node:20, golang:1.22, php:8.3-apache
WORKDIR /app
COPY <файли-залежностей> .            # package.json / go.mod / composer.json
RUN <команда-встановлення-залежностей># npm ci / go mod download / composer install
COPY . .
RUN <команда-збірки-якщо-потрібна>    # напр. npm run build
EXPOSE <порт>
CMD ["<команда>", "<запуску>"]
```

Базовий образ під свій стек шукай на **hub.docker.com** (офіційні образи —
`node`, `python`, `openjdk`/`temurin`, `golang`, `php`, `ruby` тощо).

**Що зробити:**
1. Створити `Dockerfile` у корені проекту за відповідним варіантом.
2. Підставити свої версії, порт і команду запуску.

**Що включити у звіт:**
- Повний текст свого `Dockerfile` (код-блоком) + 1–2 речення, чому обрав(ла)
  саме такий базовий образ.

**Самоперевірка:** у `Dockerfile` є `FROM`, `WORKDIR`, `COPY`, `EXPOSE` і
команда запуску (`CMD` або `ENTRYPOINT`), а порт у `EXPOSE` збігається з тим,
який слухає застосунок.

> **Важливо:** застосунок має слухати `0.0.0.0`, а **не** `localhost`/`127.0.0.1`,
> інакше ззовні контейнера він буде недоступний.

## Завдання 2 — Додати `.dockerignore`

**Що зробити:**
1. Поруч із `Dockerfile` створити файл `.dockerignore`, щоб не тягнути в образ
   зайве (це прискорює збірку й зменшує образ). Приклад:
   ```
   .git
   .idea
   *.md
   # Java:
   build/
   target/
   # Node:
   node_modules/
   # Python:
   venv/
   __pycache__/
   ```

**Що включити у звіт:**
- Текст свого `.dockerignore`.

**Самоперевірка:** у списку є `.git` і папка артефактів/залежностей твого стеку.

## Завдання 3 — Зібрати образ

**Що зробити:**
1. З кореня проекту (там, де `Dockerfile`) зібрати образ:
   ```bash
   docker build -t <прізвище>-coursework:1.0 .
   ```
   Крапка в кінці — це контекст збірки (поточна папка).
2. Переконатися, що образ з'явився:
   ```bash
   docker images
   ```

**Що включити у звіт:**
- Скрін успішного завершення `docker build` (рядок типу `naming to ... done`).
- Скрін `docker images` зі своїм образом і його розміром.

**Самоперевірка:** збірка завершилась без помилок; образ є у списку.

---

## Завдання 4 — Запустити контейнер і перевірити

**Що зробити:**
1. Запустити контейнер зі свого образу (підстав свій порт):
   ```bash
   docker run -d -p 8080:8080 --name coursework <прізвище>-coursework:1.0
   ```
2. Перевірити, що працює: відкрити в браузері `http://localhost:8080`
   (або потрібний шлях/ендпоінт; для API можна `curl http://localhost:8080/...`).
3. Якщо щось не так — подивитися логи: `docker logs coursework`.

**Що включити у звіт:**
- Скрін `docker ps` із запущеним контейнером `coursework`.
- Скрін працюючого застосунку (сторінка в браузері або відповідь API).

**Самоперевірка:** застосунок у контейнері відповідає так само, як локально.

## Завдання 5 — (Якщо потрібна база) `docker-compose.yml`

Виконуй, **тільки якщо** твій курсовий потребує базу даних. Інакше — пропусти.

**Що зробити:**
1. У корені створити `docker-compose.yml`, що піднімає застосунок + базу разом
   (приклад — у `lr24-starter/docker-compose.yml`). Ключове: застосунок
   звертається до бази за **іменем сервісу** (напр. `db`), а не `localhost`.
2. Підняти все однією командою й перевірити:
   ```bash
   docker compose up -d --build
   docker compose ps
   ```

**Що включити у звіт:**
- Текст `docker-compose.yml`.
- Скрін `docker compose ps` з обома сервісами та скрін працюючого застосунку.

**Самоперевірка:** застосунок піднявся разом із базою однією командою й
успішно до неї підключається.

## Завдання 6 — Команда для викладача (головне завдання)

Мета — щоб викладач **однією командою** підняв твій проект у себе. Зроби
**Шлях 1** (рекомендований). Шлях 2 — як запасний/альтернативний.

### Шлях 1 (рекомендований) — опублікувати образ у Docker Hub

```bash
docker login
docker tag <прізвище>-coursework:1.0 <твій_dockerhub_логін>/coursework:1.0
docker push <твій_dockerhub_логін>/coursework:1.0
```

Тоді викладачу достатньо **однієї** команди (нічого не клонуючи й не збираючи):
```bash
docker run -d -p 8080:8080 <твій_dockerhub_логін>/coursework:1.0
```
А якщо проект із базою (Завдання 5) — опублікуй і додай `docker-compose.yml`,
тоді команда викладача: `docker compose up`.

### Шлях 2 (запасний) — з вихідного коду

Якщо не хочеш публічний образ — надішли репозиторій із `Dockerfile`, і викладач
збере сам:
```bash
git clone <посилання-на-репозиторій>
cd <папка>
docker build -t coursework:1.0 .
docker run -d -p 8080:8080 coursework:1.0
```

**Що включити у звіт:**
- **Точну команду** (або кілька рядків), якою викладач підніме твій проект.
- Скрін успішного `docker push` (для Шляху 1) — видно `pushed` і назву репозиторію.
- Посилання на образ у Docker Hub (Шлях 1) або на репозиторій (Шлях 2).

**Самоперевірка:** ти **сам(а) перевірив(ла)** команду «з чистого аркуша» —
напр. видалив локальний образ (`docker rmi`) і запустив тільки своєю фінальною
командою; проект піднявся й відкрився.

# Поради

**Скріни:** macOS `Cmd+Shift+4`; Windows `Win+Shift+S`; Linux `Shift+PrintScreen`.

**Якщо щось не працює:**

1. **`docker build` падає на `COPY`.** Перевір шляхи: вони відносні до кореня
   проекту (контексту збірки). Файл, який копіюєш, не має бути в `.dockerignore`.

2. **Контейнер стартує і одразу `Exited`.** Дивись `docker logs <name>` —
   там реальна причина (не та команда в `CMD`, не той порт, бракує змінної).

3. **Сторінка не відкривається, хоча контейнер `Up`.** Найчастіше застосунок
   слухає `127.0.0.1`/`localhost` всередині контейнера — поміняй на `0.0.0.0`.
   Також перевір, що ліва частина `-p` (`8080:`) збігається з портом, на який
   ти стукаєш у браузері.

4. **`port is already allocated`.** Прибери старий контейнер `docker rm -f <name>`
   або зміни лівий порт: `-p 8090:8080`.

5. **`docker push` → `denied: requested access`.** Перевір `docker login` і що
   тег має формат `<твій_логін>/<repo>:<tag>` (саме твій логін на Docker Hub).

6. **Застосунку потрібна база, а він її «не бачить» у Compose.** У налаштуваннях
   підключення хост має бути **ім'я сервісу бази** (`db`), а не `localhost`.

7. **Перевір команду для викладача чесно:** `docker rmi <образ>` (видали
   локальний), потім запусти тільки своєю фінальною командою — так ти побачиш
   те саме, що й викладач.

Якщо нічого не допомогло — питай, прикріпивши `Dockerfile`, повну команду та
вивід `docker logs`.

Удачі!
