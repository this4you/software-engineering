# Лабораторна робота: Горизонтальне масштабування і балансування

## Мета

Закріпити теорію з лекції «Хмарні технології» на практиці. Ти запускаєш
простий веб-додаток локально, поетапно масштабуєш його до кількох реплік
за nginx-балансувальником, спостерігаєш проблему stateless-стану і
розв'язуєш її через спільне сховище (Redis). У кінці бачиш, як кластер
переживає падіння однієї з реплік.

Тема охоплює слайди **9** (мікросервіси, stateless), **11** (масштабованість,
load balancing), **12** (відмовостійкість), **13** (сховища), **14** (мережі).

## Передумови

- Встановлений **Docker Desktop** (на macOS / Windows / Linux).
- Базові навички: термінал, `git`.
- Стартер-репозиторій склонований у локальну папку (посилання видасть викладач).

> Свій код писати не потрібно — усі команди виконуються в терміналі або
> в браузері. Лаба не про Docker — окрема тема по контейнерах буде пізніше;
> зараз Docker для нас лише засіб локально відтворити кластер.

## Як здавати

- **Формат:** один файл `lab_scaling_<прізвище>.md` або PDF.
- **Структура файлу:**
    1. Титулка (ПІБ, група, дата).
    2. По одному розділу на кожне з 5 обов'язкових завдань.
    3. (Опціонально) розділ із бонусним завданням.
    4. Розділ «Відповіді на питання».
    5. Чек-лист самоперевірки.
- **Скріни** — вставляти прямо в MD синтаксисом `![підпис](шлях/до/файлу.png)`.
- **Здача:** як домовлено з викладачем (Google Classroom / пошта / Moodle).

# Частина 1 — Обов'язкові завдання

Усі 5 завдань нижче треба виконати і задокументувати у звіті.

---

## Завдання 1 — Запуск однієї репліки (baseline)

**Що зробити:**
1. У папці зі стартером виконати:
   ```
   docker compose build
   docker compose up -d
   ```
2. Відкрити в браузері http://localhost:8080.
3. Натиснути «Оновити» (Cmd/Ctrl+R) 5–7 разів і подивитись на поле
   **Hostname** на сторінці. Воно має лишатися незмінним — це означає, що
   запити обслуговує одна й та сама репліка.

**Що включити у звіт:**
- Скрін сторінки з видимим `Hostname` (наприклад, `web-1-a3f2c…`).
- Скрін терміналу з виводом `docker compose ps` (видно 1 контейнер `web`).
- 1 речення: що саме показує поле `Hostname` і чому воно не змінюється.

**Самоперевірка:** на сторінці видно один hostname; у `docker compose ps`
рівно один web-контейнер.

---

## Завдання 2 — Горизонтальне масштабування до 3 реплік

**Що зробити:**
1. Зупинити поточний запуск і запустити з трьома репліками:
   ```
   docker compose down
   docker compose up -d --scale web=3
   ```
2. Перевірити: `docker compose ps` — має показати 3 рядки з web-сервісами.
3. Відкрити http://localhost:8080 і 5–7 разів оновити сторінку. **Значення
   `Hostname` має змінюватися** — nginx по черзі (round-robin) направляє
   запити на різні репліки.
4. Зробити 3 послідовні скріни сторінки з трьома різними hostname (або
   склеїти у колаж).

**Що включити у звіт:**
- Скрін `docker compose ps` зі трьома web-контейнерами.
- Скрін(и) сторінки з трьома різними значеннями `Hostname`.
- 1–2 речення: який тип балансування використовує nginx і чому користувач
  бачить кожного разу інший hostname.

**Самоперевірка:** видно три різні hostname; жоден не повторюється на
сусідніх скрінах.

---

## Завдання 3 — Stateless-пастка («стрибаючий» лічильник)

**Що зробити:**
1. На сторінці натиснути кнопку **«+1»** десять разів поспіль.
2. Спостерігати за значенням лічильника. **Очікувана аномалія:** замість
   послідовності 1, 2, 3, 4… лічильник «стрибає»: 1 → 3 → 7 → 2 → 5… Послідовності
   немає, числа можуть навіть зменшуватись.

**Що включити у звіт:**
- Скрін(и) сторінки з кількома натисканнями, де добре видно «стрибки»
  лічильника (мінімум 4–5 послідовних значень з аномальними переходами).
- 3–5 речень своїми словами: чому так відбувається? Підказка: де
  зберігається значення лічильника і скільки незалежних місць у пам'яті
  існує одночасно?

**Самоперевірка:** у звіті є явний приклад непослідовних чисел і пояснення
причини, що включає слова «пам'ять процесу» або «in-memory».

---

## Завдання 4 — Виправлення через зовнішнє сховище (Redis)

**Що зробити:**
1. Зупинити систему і перезапустити з увімкненим Redis:
   ```
   docker compose down
   USE_REDIS=true docker compose up -d --scale web=3
   ```
   (Windows PowerShell: `$env:USE_REDIS="true"; docker compose up -d --scale web=3`)
2. Знову натиснути «+1» десять разів. Лічильник тепер має зростати **монотонно**:
   1, 2, 3, … 10 — без стрибків.
3. Зробити скрін сторінки з коректним послідовним значенням лічильника.

**Що включити у звіт:**
- Скрін сторінки з монотонно зростаючим лічильником.
- Скрін `docker compose ps` — видно, що серед сервісів з'явився `redis`.
- 2–3 речення: яку роль виконує Redis у цій системі і чому 3 репліки тепер
  «бачать» один лічильник.

**Самоперевірка:** лічильник зростає чітко на 1; Redis-контейнер
запущений; значення `Hostname` все одно змінюється між запитами (це
важливо — балансування не вимкнулось).

---

## Завдання 5 — Resilience: імітація відмови репліки

**Що зробити:**
1. Подивитися список контейнерів і скопіювати ID однієї з web-реплік:
   ```
   docker compose ps
   ```
2. «Вбити» одну репліку (імітація падіння інстанса в хмарі):
   ```
   docker kill <container_id>
   ```
3. Поновити сторінку 5–10 разів. **Сайт повинен продовжувати працювати** —
   тепер запити йдуть на дві репліки замість трьох.
4. Натиснути «+1» ще кілька разів — лічильник продовжує зростати коректно
   (Redis зберіг попереднє значення).

**Що включити у звіт:**
- Скрін `docker compose ps` після `docker kill` — видно одну репліку зі
  статусом `Exited` (або `unhealthy`), дві у статусі `Up`.
- Скрін сторінки після вбивства репліки — все ще працює.
- 2–3 речення: чому користувач не помітив відмови? Як це пов'язано з
  поняттями SLA, redundancy та self-healing з лекції?

**Самоперевірка:** одна репліка справді мертва (видно у `ps`); сторінка
відкривається; жоден з 10 рефрешів не дав 502 Bad Gateway.

# Частина 2 — Бонусне завдання (опціонально)

Виконуй, якщо хочеш краще зрозуміти тему. Без нього лабораторна теж
зарахована.

## Бонус — Що буде, якщо вбити сам Redis?

Запусти лабу в режимі `USE_REDIS=true` з 3 репліками. Знайди контейнер
`redis` у `docker compose ps`, потім зупини його:
```
docker stop <redis_container_id>
```
Натисни «+1» на сторінці. Що ти бачиш? Чи живе додаток без Redis? Чи живе
сторінка взагалі? Опиши у звіті своїми словами (3–5 речень) і зроби
відповідний скрін. Поясни, що цей експеримент демонструє про залежність
stateless-додатків від зовнішнього сховища (single point of failure).

# Частина 3 — Відповіді на питання

Напиши коротку відповідь (2–4 речення) на кожне:

1. **(Завдання 2)** Чому горизонтальне масштабування зазвичай дешевше і
   гнучкіше за вертикальне (купити більший сервер)? Які обмеження є у
   вертикального масштабування?

2. **(Завдання 3)** Уяви класичний монолітний веб-додаток, де сесія
   користувача зберігається в пам'яті процесу. Що станеться, якщо команда
   вирішить запустити його в трьох екземплярах за балансувальником?
   Опиши хоча б два конкретні симптоми, які побачить користувач.

3. **(Завдання 4)** У реальній хмарі Redis зазвичай не запускають як просто
   контейнер. Які керовані сервіси AWS / Azure / GCP виконують схожу роль
   зовнішнього сховища стану? Назви по одному з кожного провайдера.

4. **(Завдання 5)** SLA 99.9% означає близько 8 годин 46 хвилин downtime
   на рік. Якби кожна репліка у нашій лабі мала «справжній» SLA 99%
   (≈3.6 дня downtime/рік), скільки приблизно становив би сумарний SLA
   кластера з 3 паралельних реплік, які виходять з ладу незалежно? Чому
   redundancy «множить дев'ятки»?

5. **Загальне** Назви хоча б один тип додатку, який **не можна** просто
   масштабувати горизонтально через `--scale=N`. Чому?

# Поради

**Скріни:**
- macOS: `Cmd + Shift + 4` (виділена область) або `Cmd + Shift + 5` (меню).
- Windows: `Win + Shift + S` (інструмент «Знімок екрана»).
- Linux (GNOME): `Shift + PrintScreen`.

**Вставка картинки в MD:**
```markdown
![Три різні hostname після scale=3](images/task2-three-hostnames.png)
```
Папка `images/` має лежати поруч із твоїм `.md` файлом.

**Якщо щось не працює:**

1. **Порт 8080 зайнятий.** Інший процес уже слухає його. Зміни у
   `docker-compose.yml` рядок `8080:80` на `8081:80`, перезапусти.

2. **Hostname не змінюється у Завданні 2.** Перевір, що сервіс справді
   масштабовано: `docker compose ps` має показати три рядки `web`. Якщо
   ні — повтори команду `docker compose up -d --scale web=3`.

3. **Браузер кешує сторінку** і ти бачиш «застряглі» дані. Натисни
   `Cmd/Ctrl+Shift+R` (жорстке оновлення) або відкрий у режимі
   приватного перегляду.

4. **Лічильник не зростає у Завданні 4.** Перевір змінну середовища:
   ```
   docker compose exec web env | grep USE_REDIS
   ```
   Має бути `USE_REDIS=true`. Якщо ні — перезапусти з правильно
   виставленою змінною.

5. **Помилка 502 Bad Gateway після `docker kill`.** Поновлюй сторінку
   ще раз — nginx може потребувати кілька секунд, щоб виключити мертву
   репліку з ротації. Якщо помилка повторюється — переконайся, що
   жива хоча б одна репліка (`docker compose ps`).

6. Якщо нічого не допомогло — питай викладача, прикріпивши скрін помилки
   і вивід `docker compose ps`.

Удачі!
