# Лабораторна робота
**Тема:** Організація Software Configuration Management для навчального проєкту

## Мета роботи
Навчитися застосовувати базові практики **Software Configuration Management (SCM)** у програмному проєкті: визначати об’єкти конфігурації, організовувати контроль змін, будувати traceability, фіксувати baseline і працювати з релізами.

## Очікувані результати навчання
Після виконання лабораторної роботи студент повинен уміти:
- пояснювати роль SCM у сучасній розробці;
- визначати **configuration items** у проєкті;
- організовувати зміни через **issue → branch → commit → PR**;
- фіксувати **baseline** та створювати **release tag**;
- готувати короткий **changelog**.

---

## Загальна умова
Студент використовує власний або навчальний Git-проєкт.  
Це може бути:
- простий вебзастосунок;
- консольний застосунок;
- REST API;
- frontend-проєкт;
- будь-який невеликий навчальний репозиторій.

Проєкт має містити щонайменше:
- вихідний код;
- файл документації `README.md`;
- хоча б один конфігураційний або інфраструктурний файл.

---

# Завдання лабораторної роботи

## Завдання 1. Визначення configuration items
Проаналізуйте структуру проєкту та визначте, які елементи є **configuration items**, тобто повинні перебувати під контролем SCM.

### Потрібно:
1. Виділити не менше **5 configuration items**.
2. Для кожного елемента коротко пояснити:
    - що це за об’єкт;
    - чому він важливий;
    - як його зміна може вплинути на продукт.

### Приклади можливих configuration items:
- вихідний код;
- `README.md`;
- `openapi.yaml`;
- `Dockerfile`;
- `.github/workflows/...`;
- `docker-compose.yml`;
- SQL-міграції;
- `.env.example`;
- deployment-конфіги.

### Результат:
Подати таблицю виду:

| № | Configuration item | Призначення | Чому має бути під SCM |
|---|---|---|---|

---

## Завдання 2. Організація контрольованої зміни
Реалізуйте одну невелику зміну в проєкті через контрольований workflow.

### Приклади змін:
- додати новий endpoint;
- змінити повідомлення в UI;
- додати нову кнопку;
- виправити невеликий баг;
- змінити конфігураційний параметр;
- додати новий пункт у документацію.

### Потрібно:
1. Створити **issue** або текстовий опис запиту на зміну.
2. Створити окрему **гілку** для реалізації зміни.
3. Виконати зміну.
4. Зробити щонайменше **1 commit** із зрозумілим повідомленням.
5. Створити **pull request**.
6. Виконати **review** зміни:
    - самостійно або з іншим студентом;
    - зафіксувати короткий результат перевірки.
7. Злити зміну в основну гілку.

### Результат:
У звіті має бути:
- назва issue;
- назва branch;
- commit hash або скріншот;
- посилання або скріншот pull request;
- короткий опис перевірки.

---

## Завдання 3. Побудова traceability
Покажіть, як простежується зміна від її ініціації до включення в продукт.

### Потрібно побудувати ланцюг:
**Issue → Branch → Commit → Pull Request → Merge**

### У звіті вкажіть:
- яка задача породила зміну;
- у якій гілці вона реалізовувалась;
- який commit її містить;
- через який PR вона пройшла;
- коли і куди була змерджена.

### Результат:
Подати traceability у вигляді схеми або таблиці:

| Етап | Ідентифікатор / назва | Пояснення |
|---|---|---|

---

## Завдання 4. Формування baseline
Після успішного merge визначте стабільний стан системи та зафіксуйте його як **baseline**.

### Потрібно:
1. Обґрунтувати, чому саме цей стан можна вважати стабільним.
2. Вказати, що входить до baseline:
    - код;
    - документація;
    - конфігурації;
    - інші важливі елементи.
3. Позначити цей стан у репозиторії:
    - через **tag**, або
    - через чітко описаний baseline у звіті.

### Результат:
Короткий опис baseline:
- назва baseline;
- дата створення;
- що до нього входить;
- чому він вважається стабільним.

---

## Завдання 5. Release management
Створіть простий навчальний реліз на основі сформованого baseline.

### Потрібно:
1. Призначити **номер версії** у форматі, наприклад:
    - `v1.0.0`
    - `v1.1.0`
2. Створити **release tag**.
3. Підготувати короткий **changelog**, у якому вказати:
    - які зміни увійшли в реліз;
    - що було додано або виправлено;
    - до якого baseline прив’язаний реліз.

### Результат:
Подати changelog у вигляді списку.

# Вимоги до звіту
Звіт повинен містити:

1. Тему, мету та короткі теоретичні відомості про SCM.
2. Опис використаного проєкту.
3. Результати виконання всіх завдань 1–5.
4. Скріншоти або посилання на:
    - репозиторій;
    - issue;
    - branch;
    - commit;
    - PR;
    - tag.
5. Висновки.

# Контрольні питання
1. Що таке SCM і чим він відрізняється від Git?
2. Що таке configuration item?
3. Чому baseline є важливим для релізів і rollback?
4. Що таке traceability і навіщо вона потрібна?
5. Чим release management пов’язаний із SCM?
6. Які об’єкти, окрім коду, можуть бути під контролем SCM?

---

# Критерії оцінювання
### Оцінюється:
- коректність визначення configuration items;
- наявність контрольованого workflow зміни;
- логічність побудови traceability;
- правильне розуміння baseline;
- наявність release tag і changelog;
- повнота та охайність звіту.

---

# Висновок для студента
У цій лабораторній роботі потрібно не просто використати Git, а показати, що студент розуміє **SCM як систему керування змінами всього продукту**, включно з кодом, конфігураціями, baseline, traceability і релізами.
